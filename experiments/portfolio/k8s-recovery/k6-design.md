## Campaign identity and exact grant read

**Approval flow.** Use a dedicated runner-side scripted process and a private decision adapter on the same runner, outside application pods. Bind the adapter only to a protected local Unix socket (directory 0700, socket owner access only). Remove the operator Deployment, Service and operator token mount from the K6 rendering. Neither application's API exposes operator writes. Setup alone provisions identities. Give the running approver no kubeconfig, service-account mint permission, DB writer credential or host control socket.

1. In each fresh episode namespace create ServiceAccount `k6-approver` with automount off and no RoleBindings. At warmup start, setup requests a short-lived, bound TokenRequest token for this account, sole audience `dur053-k6-approval`, bound to an episode-owned Secret UID. Use the pinned kind issuer `https://kubernetes.default.svc.cluster.local` and a 600 s requested authentication-token TTL. Limit each token to this episode and validate the returned expiry against the planned arrival schedule. Refuse to start the episode unless remaining validity covers the last planned arrival + 2L. Deliver by private descriptor/file to the runner-side approver. The adapter uses the trusted kind API CA and a distinct reviewer credential with only create TokenReview. Verify the exact issuer, sole audience, expiry, authenticated review response, SA UID and subject `system:serviceaccount:<episode-namespace>:k6-approver`. Check the bound object against trusted episode inventory. Revoke by deleting the bound object at closeout. Credential rotation during the job cannot extend a grant.
2. Derive the permitted workflow, node, iteration, resource, expected revision, canonical arguments and stable key from the sealed load plan and durable submission-key mapping. The scheduler recognizes a cooperating node, derives this proposal and calls the existing lease-fenced CreateApprovalIntent before allocating a dispatchable attempt. The scripted approver reads a pending proposal by the exact expected identity through the private adapter, independently recomputes the hash from the plan and records the decision for that intent and hash only. Reuse the scripted decision pattern in `python/incident_agent/dur056_evaluation.py:44`, `:217` and the actual store flow in `cmd/m5-fixture/main.go:386`; neither fixture actor literal authenticates a caller.
3. Adapter DB identity `k6_decision_writer` can execute only an episode-scoped pending-intent lookup and record-decision operation. Expose the exact-hash, pending/expiry and same-actor idempotency logic of `RecordApprovalDecision` through this restricted operation. The DB wrapper fixes the episode namespace and expected approver subject at provisioning. The adapter attributes the decision from TokenReview. Deny table DML, arbitrary intent creation, application, cancellation, renewal and dispatch. Return the decision identity, never a grant credential. Preserve rejection and pending cancellation order. On a scheduler scan of WAITING_APPROVAL, the actual lease holder locks lease then workflow, checks revision/intent/cancellation, applies the decision with `ApplyApproval` and commits history/outbox. Exactly one grant per logical operation survives redispatch. Never hand a lease reference to the scripted approver.
4. A worker may obtain a scoped dispatch envelope only after its authenticated successful current claim, from worker-control. Bind workflow, node, iteration, attempt, resource, key, canonical state/hash, expected resource revision, grant and issued resource-local fence to that claim. Worker-control requests fence allocation over a mutually authenticated engine-to-sink channel for the exact persisted grant and attempt. Make allocation idempotent by that tuple, store the mapping in the sink DB, and return the same token on a retried claim response. Workers have no allocator permission. The broker carries transport identity. Neither broker text, request body actor, tool/model output nor a worker-chosen target grants authority. Use a dedicated projected worker audience for sink apply/lookup and authenticated TLS. Keep grant secrets out of broker payloads, witness, command arguments, HTTP logs, snapshots and release assets.

**Reader interface.** One episode database, one sink-only login `k6_sink_grant_reader`, TLS with verified server identity and private per-episode credential. Revoke PUBLIC defaults, CONNECT to other campaign databases, schema CREATE, TEMP and role inheritance. Revoke PUBLIC EXECUTE on the lookup and decision functions at creation, fix the definer search path to trusted schemas with pg_temp last, fully qualify objects and use typed parameters without dynamic SQL. Grant CONNECT to this DB, USAGE on `k6_auth`, EXECUTE on one fixed-search-path read function. No SELECT on a table or listable view, write function, grant-token column or engine checker interface. Use a NOLOGIN, least-privileged function owner with column SELECT on a private security-barrier view `k6_auth.episode_grants` joining `engine.approval_action_intents` to `engine.workflow_executions` by workflow ID and the provisioned namespace. The namespace is fixed by trusted installation, never session-settable by a client.

## Phase C connection evidence

The hosted Phase C artifact (`dur053-k6-c-<run_id>`) contains
`connection-trace.json`. The sampler retains the grouped engine and sink
snapshots in `samples` before applying the settings, pair and total budgets.
Each entry in `rejections` gives the zero-based sample index, server, failure
reason, PostgreSQL capture time in epoch microseconds and per-backend
observations from the rejected snapshot. A backend record contains its PID,
backend start time, state, role, application, wait-event type, wait event and
namespace pod name. SQL NULLs and unresolved pod names are recorded as JSON
`null`. The trace contains no raw client addresses, credentials or SQL query
text. A run with no rejected observations carries `"rejections": []`.

A backend is starting only when the role is SQL NULL and the application name
is the empty string. It counts immediately toward the total connection budget.
The sampler follows that PID and backend start time for up to 2 seconds, with
at most 200 milliseconds between observations. The backend must resolve to a
registered pair within that pair's budget. An unresolved, vanished, late or
over-budget backend fails the gate. Other unknown pairs fail immediately.
`startups` records the tracked backend before and after each follow-up with the
outcome, including an empty observation if the backend disappears. Pod names
are diagnostic fields. The same gate applies to both databases.

Each initial snapshot and its follow-ups use one autocommit `psql` session.
The trace keeps the sampler's PostgreSQL PID and counts its registered
application in every snapshot. PostgreSQL statement timestamps govern the
2-second resolution bound and the 200-millisecond gap bound. In the
`PostgreSQL K6 fixtures and parity` job, a raw TCP client on the isolated pinned
PostgreSQL 18.6 instance withholds a password, then either authenticates or
disconnects. Its `connection-trace.json` and `startup-fixture.json` are stored
under `k6-phase-c-startup/` in the service-race diagnostics artifact.

   - **(b)** A recovery after the cutoff sees the expired-grant rejection, keeps OUTCOME_UNKNOWN / RECONCILIATION_REQUIRED visible, and publishes it as an engine outcome of that episode. It is never retried with a fresh intent or grant. The protocol's no-renewal rule stands.
